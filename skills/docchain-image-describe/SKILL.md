# docchain-image-describe — 文档图片转文字

把一篇（或几篇）文档里的每张图片交给多模态模型，生成中文描述插在图片上方，存成该文档的**旁路描述 md**。主 md 不会被动，描述 md 是独立文件，用 `read_format=image_description_md` 读取。

## 典型用法

```
把《大语言模型从理论到实践》里的图片都转成文字
帮我搜名字带"大语言模型"的文档，我自己选一篇
125755 的图片描述生成好了吗？读出来看看
这台机器上能用哪些视觉模型？
```

> 用户主动说"先跑 2 张"时才限量处理；**不要自己主动拆成两轮**。试跑既判断不出描述质量，还会让用户重复选一次模型。

## 工具参数

| 参数 | 必填 | 默认值 | 说明 |
|------|:----:|:-----:|------|
| `doc_ids` | ❌ | - | 文档 ID 数组。为空时必须给 `keyword` 或 `list_models` |
| `keyword` | ❌ | - | 文档名关键字：**只返回候选清单**，不描述、不保存 |
| `topic_ids` | ❌ | 配置页选中主题 | 候选模式的搜索范围 |
| `max_images` | ❌ | 0（全部） | 每篇最多处理几张。默认一次跑完整篇 |
| `concurrency` | ❌ | 8 | 同时处理几张，上限 10（实测 12 起被网关限流） |
| `dry_run` | ❌ | false | 只生成不保存，返回统计与预览 |
| `judge_model` | ❌ | 见下 | 结构图的**复核模型**。不传 = 从候选清单里挑一个与主模型不同的；传空串 = 只读一遍，省一半调用 |
| `list_models` | ❌ | false | 只列出当前 key 可用的视觉模型 |
| `read` | ❌ | false | 只读取已生成的描述 md |
| `confirm` | ❌ | false | 批量（>1 篇）时必须显式确认才执行 |
| `diagram` | ❌ | `on` | `on`：先分类，**结构图出 `plantuml` 草图、其它图出中文描述注释**；`off`：不分类不出草图，全部只写描述注释 |

> 工具**没有 `model` 参数**。视觉模型只能跟随对话模型，或由用户在弹窗里点选 —— 见下节。

## 每张图走哪条路（分类规则）

每张图先单独问一次模型「该出结构还是该写描述」，只回答一个词。两种产物**二选一，不并存**：

```
STRUCTURE → 一段 ```plantuml 代码块（不写注释）
PROSE     → 一条 <!-- image-desc: … --> 注释（不写草图）
```

无论哪种，原图都不再嵌进正文，统一改成一行 `[原图](地址)` 链接。

### 判定口径

以下两条**同时满足**才判 STRUCTURE：

1. 图中有**连接线**（箭头、实线或虚线）把不同的方框连起来；
2. 去掉这些连线后，方框之间的先后 / 包含 / 流转关系就**无从得知**。

任何一条不满足 → PROSE。核心思想：**信息是不是由「连接关系」承载的**。

### 归属速查

| 图像特征 | 判为 | 为什么 |
|---|---|---|
| 流程图、时序图、状态图 | STRUCTURE | 箭头走向就是信息 |
| 系统架构图、模块框图 | STRUCTURE | 谁调谁、谁连谁是信息 |
| 组织架构图，**上级用线分叉连到下属** | STRUCTURE | 那些分叉线就是层级 |
| 组织架构图，**框与框之间没有任何连线** | PROSE | 光有方框，没有可读的关系 |
| 靠色块分区 / 左右分栏 / 竖排标注表达层级的版式图、信息图、海报 | PROSE | 关系靠位置和颜色，代码表达不出来 |
| 框里是成段说明文字、职责描述、宣传文案 | PROSE | 那是文案，不是模块名 |
| 照片、界面截图、曲线图、柱状图、表格 | PROSE | 不是结构 |

> **关键区分**：两张图可能都没有箭头，但分类结果不同。区别在于「有没有线真正连接两个框」，而不是「有没有箭头」。
>
> 例：事业群向下拉出细线分叉指向每个下级 → 有线，STRUCTURE；蓝框绿框分区、框间无连线 → 无线，PROSE。

### 为什么规则偏向写描述

判错的代价不对称：

- 该画图却写了描述 → 损失一次便利；
- 该写描述却画了图 → 产物变成一堆无意义方框，**比没有还差**。

所以规则刻意往「宁可写描述」偏。

### 三道兜底

| 机制 | 触发条件 | 行为 | 计数 |
|---|---|---|---|
| **可疑复核** | 判成 PROSE，但回答里出现了图数据签名 `"nodes":` | 补问一次结构提示词，能出图就改判为图 | `diagram.suspect` |
| **版式图兜底** | 判成 STRUCTURE，但「节点名」里 ≥3 个且 ≥25% 是版面标注 | 认定是版式图，退回描述 | `diagram.annotation_guard` |
| **不可用回退** | 给了 JSON 但不可用（截断 / 节点<3 / 边<2 / 边悬空） | 先补一次纯描述调用，补不到才记失败 | `diagram.prose_retry` |

> 「版面标注」的判据是含句读 `：，。；、` 或分层间隔号 `·`。
> **省略号 `…` 不算证据** —— 那是截断长名字留下的痕迹，拿它判会把正常架构图误伤。

## 视觉模型怎么选

只有一个来源，加一个兜底：

1. **跟随当前对话模型** —— 对话里选哪个模型，就用哪个读图。
2. **对话模型读不了图时由用户点选** —— 工具暂停并弹窗，按综合能力列出**前 5 个**视觉模型（顺序见下，可用配置项 `docchain_vision_candidates` 覆盖）。用户点一个后流程继续。

第 2 种选择**只对本次调用生效**，不会改动对话模型；用户不选就中止，不会有人替他决定。想长期用视觉模型，请直接在对话模型下拉里切换。

**复核模型**从同一份候选清单里挑第一个「可用且与主模型不同」的。同一张图不能用一个模型读两遍 —— 那样拿不到第二视角。候选里没有别的可用模型时不做复核（`diagram.dual` 为 0）。

### 判定「对话模型能不能读图」用白名单

工具拿对话模型名去网关 `/models` 清单里查 `is_vision`，结论有三种：

| 查到的结论 | 工具行为 |
|---|---|
| `true`（明确是视觉模型） | **直接用**，不弹窗 |
| `false`（明确不是） | 弹窗让你选 |
| **查不到**（模型不在清单 / 网关限流 / 网络错误） | **同样弹窗让你选** |

**关键**：只有「确定能读图」才放行，**查不到也当不能用**。

> 这条是踩过坑改的：早先"查不到就放行"，实测出现过 —— 对话模型是 `deepseek-flash`，它不在网关清单里 → 判成未知 → 不弹窗 → 拿它去发请求先 404 → **静默降级到 `g-deepseek-v4-flash` 读图**。用户全程没参与选型，最后读图用的根本不是他以为的那个模型。
>
> 代价也认：网关临时限流导致清单拉不到时，会多弹一次选择框。但这比"悄悄换了个模型替你读图"要好。

### 候选顺序来自实测横评

5 个模型 × 6 张真实组织架构图 × 每张 2 次，判分标准是「根的直接下级数量对不对」：

| 排名 | 模型 | 综合分 | 两排平级 | 多层树 | 真实文档 | 简单扇出 | 宽扇出10 | 版式图 |
|:--:|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| 1 | **doubao-seed-2.0-pro** | **100** | 100 | 100 | 100 | 100 | 100 | 100 |
| 2 | **g-doubao-seed-2.1-pro** | **100** | 100 | 100 | 100 | 100 | 100 | 100 |
| 3 | qwen3-vl-plus | 69.9 | **0** | 100 | **19** | 100 | 100 | 100 |
| 4 | glm-5v-turbo | 60.5 | 100 | 100 | **13** | **0** | 50 | 100 |
| 5 | g-gpt-5.6-sol | 未测 | — | — | — | — | — | — |

**怎么读这张表**：

- **单层扇出的树，前四个都能读对**；
- **只有 doubao 两个在两排平级的组织架构图上稳**。qwen 在这类图上会编出一层"办公室管部门"，根下级只认出 6/31；
- glm 的问题是**不稳定**：能读对的图读得很准，但会把「简单扇出」整张误判成普通描述，一张草图都不出；
- 两者速度都偏慢，单次 10–130 秒不等，还容易 429。

**关键证据**：换成最小提示词（什么都不教），qwen 在两排平级图上依然 0/2 全错。说明这是模型**读图时**就把结构看错了，不是提示词能修好的。

> 提示词能修的：漏方框、改名字、忘记顶层标题框。
> 提示词修不了的：把"同一层的两排"读成"上排管下排"。

## 调用示例

**`docchain_image_describe`** 由宿主直接执行，**不要手工跑脚本**。

```js
// 先看候选
{ keyword: "大语言模型", topic_ids: [10904] }
// 正式跑
{ doc_ids: [125755] }
// 批量：先返回清单，再确认
{ doc_ids: [125755, 125676] }  →  { doc_ids: [125755, 125676], confirm: true }
// 读回
{ doc_ids: [125755], read: true }
// 看可用模型
{ list_models: true }
// 只要描述、不要草图
{ doc_ids: [125755], diagram: "off" }
// 限量（大文档控成本时才用，不要拿它试效果）
{ doc_ids: [125755], max_images: 2 }
```

## 拿到结果后必须做的事

1. **候选模式**（`mode: "candidates"`）：把候选按表格列给用户选。**不要自己替他选**，也不要直接开跑。
2. **描述模式**（`mode: "describe"`）：报告 `described / unique`、耗时、`failed` 列表、`partial`。
3. **`partial: true`**：只处理了前 N 张，其余没描述，必须明确告诉用户。
4. **`read` 模式**：把 `preview` 呈现给用户；`NOT_GENERATED` 说明还没生成过。
5. **`warnings` 非空**：把警告码和含义转述给用户，重点是 `DIAGRAM_*` 系列（见[警告码速查](#警告码速查)）。

## 失败码

返回 `{ "ok": false, "error": "...", "message": "..." }`（批量时每篇各带自己的 error）。

| error | 含义 | 怎么办 |
|-------|------|--------|
| `CONFIG` | 缺 docchain/vision 配置、没有可用参数 | 按 message 补配置 |
| `NOT_FOUND` | doc_id 不存在 | 核对 ID（先 `docchain_doc_search`） |
| `NO_CONTENT` | 主 md 为空 | 该文档还没解析出 md |
| `NO_IMAGES` | md 里没有图片引用 | 换一篇 |
| `NO_RESULTS` | 名字搜不到文档 | 换关键字或放宽 `topic_ids` |
| `NOT_GENERATED` | 还没生成过描述 md | 先跑一次生成 |
| `SOURCE_CHANGED` | 处理期间主 md 被改 | 重跑 |
| `SAVE_FAILED` | 保存接口返回非 success | 看 message 里的原始响应 |
| `SAVE_UNVERIFIED` | 保存成功但读回不一致 | 重跑；仍失败说明服务端有问题 |
| `SAVE_WRONG_TARGET` | 保存走了"覆盖主 md"分支，**已自动写回原内容** | 主 md 已恢复，把这条反馈给后端 |
| `RESTORE_FAILED` | 主 md 被覆盖且写回失败 | 用 `/v1/doc/redo_markdown` 重新解析 |
| `ALL_FAILED` | 所有图片都没生成描述 | 检查网关连通与模型权限 |
| `MODEL_UNAVAILABLE` | 主/降级模型都不可用 | 用 `list_models` 看可用清单 |
| `RATE_LIMITED` | 持续 429 | 降低 `concurrency` 后重试 |

## 结果字段速查

### 顶层

| 字段 | 含义 |
|---|---|
| `described` / `unique` | 已描述张数 / 去重后的图片总数 |
| `partial` | true = 只处理了前 N 张（`max_images` 限制） |
| `compressed` | 超长被模型压缩过的条数 |
| `truncated` | 最终仍被硬截断的条数 |
| `incomplete` | 撞上 max_tokens、内容停在半句的条数 |

> **`truncated` 或 `incomplete` 非 0 才说明真的丢信息**；`compressed` 不算丢信息。

### `diagram` 分类计数

| 字段 | 含义 |
|---|---|
| `structured` / `as_prose` | 判成结构图 / 描述图的张数 |
| `rendered` / `fallback` | 成功出草图 / 想出图但数据不可用、已回退成注释的张数 |
| `suspect` | 判成描述、但回答里出现图数据、补问过一次的张数 |
| `annotation_guard` | 判成结构、但节点多是版面标注、被退回描述的张数 |

### `diagram` 完整性计数（**非 0 都要看**）

| 字段 | 含义 | 对应警告 |
|---|---|---|
| `trimmed` | 为适配版面被裁掉的节点数 | `DIAGRAM_TRIMMED` |
| `speculated` | 推断出来的虚线边数（原图无此关系） | `DIAGRAM_SPECULATED` |
| `labels_truncated` | 节点名被截断的个数 | `DIAGRAM_LABEL_TRUNCATED` |
| `missing_from_primary` | 复核认出、主模型漏认的节点数 | `DIAGRAM_MISSING` |
| `under_read` / `under_read_fixed` | 自报方框数多于列出数的张数 / 补问补回的张数 | `DIAGRAM_UNDER_READ` |
| `orphans` | 没有任何连线的节点数（多半是顶层标题框漏认） | `DIAGRAM_ORPHAN` |
| `wrong_parent` | 两个模型对同一节点**上级**说法不同的个数 | `DIAGRAM_WRONG_PARENT` |
| `serialized_siblings` | 疑似把平级兄弟读成一条链的张数 | `DIAGRAM_SERIALIZED` |
| `group_inner_edges` | 落在同一平级分组内部的连线数（自相矛盾） | `DIAGRAM_GROUP_INNER` |
| `checked` / `check_failed` | 触发"不看图重述"自检的张数 / 判定有问题的张数 | `DIAGRAM_CHECK_FAILED` |

### `diagram` 其它

| 字段 | 含义 |
|---|---|
| `grouped` | 有平级分组的张数 |
| `judge_model` / `dual` / `agreed` / `dual_fallback` | 复核模型名 / 做了二次读图的张数 / 交集可用的张数 / 退回主模型的张数 |
| `prose_retry` | 结构数据不可用、补了一次纯描述才拿到注释的张数 |
| `mode` | `on` / `off` |

## 警告码速查

| 警告码 | 含义 | 要做什么 |
|---|---|---|
| `DIAGRAM_TRIMMED` | 草图被裁掉了节点，比原图少东西 | 必须回看原图 |
| `DIAGRAM_SPECULATED` | 有虚线边是推断的，原图并无该关系 | 对照原图确认 |
| `DIAGRAM_MISSING` | 复核比主模型多认出节点，主模型可能少画 | 对照原图确认 |
| `DIAGRAM_UNDER_READ` | 模型自报方框数多于列出数（它承认漏了） | 对照原图确认是否漏了部门 |
| `DIAGRAM_ORPHAN` | 有节点没有任何连线，多半是顶层标题框漏认 | 对照原图确认这些节点的归属 |
| `DIAGRAM_WRONG_PARENT` | 两个模型对某节点的上级说法不同（方向不冲突，只查反向边发现不了） | 对照原图确认归属 |
| `DIAGRAM_LABEL_TRUNCATED` | 节点名超 28 字符被截断，可能被改名 | 核对原名（警告里给了对照） |
| `DIAGRAM_SERIALIZED` | 疑似把平级兄弟读成一条链 | 对照原图确认层级 |
| `DIAGRAM_GROUP_INNER` | 组内出现上下级连线，与"它们是兄弟"矛盾 | 对照原图确认 |
| `DIAGRAM_CHECK_FAILED` | 只读结构的复述自检发现层级矛盾 | 对照原图确认 |
| `DIAGRAM_FALLBACK` | 给了结构数据但用不了，已回退成注释 | 看是否需要重跑 |
| `DIAGRAM_NONE` | 本次没有一张图出草图 | 全是普通图，正常 |
| `SOURCE_HAS_DESC` | 主 md 里已有旧注释，会被剥掉重写 | 正常，替换而非叠加 |
| `LARGE_PAYLOAD` | >400 张图，描述 md 可能超 2 MB | 确认接口请求体上限 |

## 草图可靠性：会被检测的错误

草图**语法一定合法**（由脚本按固定模板生成），但**结构可能有误** —— 它来自模型看图判读。这里按错误类型分组说明。

### 一、数量错（少画 / 多画）

| 错误 | 检测方式 | 计数 |
|---|---|---|
| 漏读方框 | 模型先自报 `boxCount`，再逐个数节点；自报数 > 列出数 = 它自己承认漏了，**补问一次** | `under_read` |
| 主模型少画、复核有 | 两边节点集比对 | `missing_from_primary` |
| 版面放不下被裁 | 按"删最边缘叶子"裁剪并记账 | `trimmed` |

> **不漏方框是硬要求**：提示词要求"方框一个都不能省略"，工具侧不限制节点数量（原写的"不超过 20 个"与代码上限 80 矛盾，等于让模型主动漏读，已删除）。扇出上限 40 —— 组织架构图天生就是一个中心挂二三十个平级部门。

### 二、关系错（数对得上，但"谁归谁管"错了）

这类错**最隐蔽**：节点一个不少、线也全在，所有数量类校验都是绿的。

| 错误 | 典型样本 | 检测方式 |
|---|---|---|
| **平级兄弟被读成一条链** | 事业群下挂 6 办公室 + 20 产品线，全平级无箭头；模型按"从上往下念"连成链，20 条产品线全挂到最后一个办公室下面 | **结构指纹**：父节点扇出 ≥3、且 ≥80% 的子节点彼此连成了链（≥3 条）→ `serialized_siblings` |
| **组内互连** | 模型自己把一批框圈成平级组，却又画了它们之间的上下级线 | 组内出现连线 = 硬矛盾 → `group_inner_edges` |
| **层级整体读错** | 以上两种都没命中，但产物自相矛盾 | **不看图重述自检**：只把结构喂回模型（不给图），让它复述"谁归谁管" → `check_failed` |
| **顶层标题框漏认** | 模型把最顶上的框只写进 `title`、没算作节点，于是它下面一整层全没了上级 | 检测孤立点 → `orphans` |

### 平级分组机制（重点）

为了让模型**主动**回答"这些是兄弟还是上下级"，提示词要求它在出 JSON 时**先分组、再连边**：

```json
{"nodes":[…], "edges":[…],
 "groups":[{"label":"这一组的名字","members":["n1","n2"]}]}
```

约束：一组至少 2 个成员；同一节点只能属于一组；**组内成员之间不要连边**。

渲染时分组包进 PlantUML `package {}`，人一眼能看出"这批是兄弟、不是一条链"。

**实测效果**（同一张反复读错的图）：

- 改前：郑州研发中心下 3 个团队只读出 2 个，还把「南京前端一团队」错挂到郑州下面；
- 改后：3 个全对，南京下 4 个也全对，自动圈出 3 个平级分组。

> 局限：模型可能**分组不完整**（比如 7 个平级中心只圈了 6 个，漏掉"综合规划部"）。分组是辅助信号，不是保证。

### 不看图重述自检

只对**结构可疑**的图触发（有串链指纹或组内互连），不是每张都跑：

1. 把产物结构压成文字（"X 的直接下级（N 个）：…"）；
2. **不给图**，让模型回答三个问题：有没有下级数反常的节点、有没有把平级连成链、有没有其它层级矛盾；
3. 首词 `OK` 判无问题，其余按有问题并保留原文。

原理：模型读**版面**会错，读**文字**几乎不会 —— 用强项校验弱项。

> 局限（实测）：模型若已把结构记错，喂回文字它照样按错的读。它能抓的是"数据自相矛盾"，抓不到"数据整体都错且自洽"。

### 三、其它已知偏差

| 情况 | 说明 |
|---|---|
| 名字被截断 | 超过 28 字符截短（「郑州开发一团队」→「郑州开发一团」），原名记在 `labels_truncated` |
| 时序图 | 不会画成"参与者 + 消息"的标准时序图，一律按方框 + 箭头竖排 |
| 画法单一 | 所有结构图统一竖排渲染（阅读区窄，横排必被裁） |

### 四、孤立点（顶层标题框漏认）

模型常把图最顶上那个框只写进 `title`，不当成节点。后果是它下面**一整层都没有上级**。

实测样本：「综合业务产品线」不是节点时，下面 7 个单位全成孤儿，其中没有下属的
「综合规划部」「西安研发中心」「南京第二研发中心」直接变成孤立点。

**旧行为（已废弃）**：孤立点被"漂浮标签"过滤器**静默删除**，不计数、不告警 —— 三个真实部门就这么没了。

**现行为**：

- **保留**所有孤立点（纯符号/编号在建节点阶段就已被 `isNoiseLabel` 筛掉，到不了这里）；
- 名字进 `diagram.orphans`，非 0 出 `DIAGRAM_ORPHAN` 警告并列出名字；
- 提示词规则 13/14 要求模型"顶层标题框也是节点""每个框都必须至少有一条边"。

> 取舍：多画一个孤立框只是不够美观，少画一个部门则永远查不到。所以宁可留着报出来。

### 五、曾经会丢数据、现已修正的行为

这几条是**工具自己**造成的损失，与模型读图是否正确无关。已全部修复，列在这里是因为它们解释了产物为什么长成现在这样。

| 旧行为（已废弃） | 后果 | 现行为 |
|---|---|---|
| **纯数字节点被当编号删除** | `Input → 64 → Output` 里的 `64`（可能是层宽/通道数）消失，前驱被**短路**接到后继，凭空多一条 `Input → Output` | `64` 保留；**不再短路造边**，端点缺失的边直接丢弃。只有纯符号（`---`、`·`）仍会被筛掉 |
| **同名同邻居的节点被合并** | 两个并行 `Worker` 合并成一个，**少一条支路** | 不合并任何节点。同名同邻居也可能是两个独立实体 |
| **公式大括号被剥掉** | `x^{a+b}` → `x^a+b`，**数学含义完全变了** | 原样保留。实测 PlantUML 能正常渲染 `{}` |
| **行内图片整行被替换** | `Before ![img](..) After` → 只剩 `[原图](..)`，正文丢失 | 按位置**只替换图片引用本身**，前后正文与一行多图之间的文字都保留 |
| **复核合并丢掉孤立节点与分组** | 一条连线有争议，节点就跟着消失；`groups` 字段静默蒸发 | 节点全部保留；`groups` 按最终节点重新校验后带出 |
| **复核只查"方向相反"的边** | 主模型说 B 归 A、复核说 B 归 Root —— 方向不冲突，错的那个被静默保留 | 新增 `wrong_parent` 比较，出 `DIAGRAM_WRONG_PARENT` 警告 |
| **连线去重只看起点终点** | `Client→Service[Request]` 与 `[Retry]` 只剩一条 | 去重键包含边标签 |

> 统一口径：**关系有争议 ≠ 节点不存在**；**看不清 ≠ 没有**；**多一个框只是不好看，少一条信息下游永远查不到**。

### 可信范围

**按图形结构类型判断，不按节点数。** 实测 26 节点的图可以全对，8 节点的图也可能错 —— 难度取决于结构形态：

| 结构形态 | 可靠性 | 说明 |
|---|---|---|
| **单层扇出**（顶部 1 个框 → 下面一排） | 高 | 结构直观，模型很少读错 |
| **多层树**（逐层分叉） | 中 | 需核对旁挂框有没有被拉平成平级子节点、行尾有没有漏节点 |
| **同一层分成两排**（如 6 个办公室 + 25 个部门并排挂在顶上） | **低** | 最容易把两排读成上下级；qwen3-vl-plus 实测 0/8 |
| **多棵树拼接的长图** | 低 | 建议改用 `diagram: "off"` 的纯文字描述 |

**核对清单**（拿到草图后必看）：

1. 顶层的框是不是只有那一个总标题，下面一层是不是都该平级；
2. 有没有节点没有上级（`orphans` 非 0 或警告 `DIAGRAM_ORPHAN`）；
3. 名字相近的框有没有被搞混（如"南京前端一团队"与"郑州前端一团队"）。

## 已知边界

### 数据与幂等

- **幂等口径**：每次从干净的主 md 重新生成，所以**结构**幂等（不会累积注释）；但模型输出有波动，重复跑产物不保证逐字相同。
- **叠层清理**：主 md 里已有旧 `image-desc` 注释时，生成时**先剥掉再写本次结果** —— 替换而非叠加，不会出现"同一张图既像草图又像注释"。
- **只处理 md 里引用的图**：平台解析阶段没抽出来的图（被水印覆盖、被判成装饰等）工具看不到。`redo_markdown` 只是用缓存重新生成 md，**不会重新抽图**，要重抽得让后台重新解析。
- **体积**：>400 张图的文档，描述 md 可能超过 2 MB。

### 规模与性能

- **规模上限**：单张结构图最多 **80 节点 / 140 条边**；渲染后超过 **6000 字符**才裁剪。这三条只是"防爆"兜底 —— 正常组织架构图（40~60 个方框）不会被裁。裁剪是最后手段：产物是给对话助手读的代码，删掉一个节点，助手就永远不知道那个部门存在。
- **并发**：8 是实测最优点；12 起 429，3/4 反而更慢（网关批处理效应）。
- **时间**：描述图 **2 次调用**（分类 + 描述），单张约 8–12 秒；结构图 **3 次**（分类 + 主读 + 复核），约 25–50 秒；可疑的再 +1 次自检。9 张图实测 1–4 分钟（网关波动大）。
- **长度**：单条上限默认 **2000** 字符。超长时**先让模型压缩**（保留名称/数值/公式，删掉修饰语），压不下来才按句末截断。
- **精度优先**：专有名词/字段名/单位/数值/公式照抄原文，纯装饰（圆角、线条、填充）与重复句一律删掉；实测比"完整还原"版短 57%，信息量反而更高。

### 清噪规则

- 丢掉：1–2 位序号（`0`…`9`）、纯符号、`L×` / `N×` / `×N` 这类重复次数；
- 保留：`4096`、`224×224×3` 这类**真实层宽 / 尺寸**。

### 配置

`docchain_vision_*` 不在插件配置页的输入框里，改设置文档或环境变量：

| 变量 | 说明 |
|---|---|
| `VISION_BASE_URL` | 网关地址 |
| `VISION_FALLBACK_MODEL` | 降级模型 |
| `VISION_JUDGE_MODEL` | 复核模型（空串 = 关闭复核） |
| `VISION_API_KEY` | 网关 Key（凭据库里的 `IWHALE_API_KEY`） |
| `VISION_MAX_DESC_CHARS` | 单条描述长度上限 |
| `VISION_DIAGRAM` | `on` / `off` |

> `VISION_MODEL` 只对**脚本命令行**生效。走工具 `docchain_image_describe` 时模型由宿主传入（跟随对话模型或用户点选），环境变量不参与 —— 它不能绕过选模型的机制。

### 置信度

描述与草图都来自多模态模型，可能有误读（尤其是密集表格与公式），关键数据请回看原图。

分类**只判一次、无自校验**：判成"描述"就会静默丢掉结构。抽查时看 `diagram.as_prose` 与 `diagram.structured`。
